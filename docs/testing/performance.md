# Phase 10F — Performance and load testing

The performance test suite is composed of two layers:

1. **API baselines** — measured latency and error-rate targets per
   endpoint, captured in `tests/performance/baselines.json`.
2. **k6 load scenarios** — sustained traffic generated by k6 against
   the staging environment, declared in `tests/performance/k6/*.js`.

## Load scenarios

The k6 scripts cover the mandatory scenarios:

```
tests/performance/k6/list-reads.js        ← sustained list reads
tests/performance/k6/document-creation.js ← oficio creation burst
tests/performance/k6/pdf-generation.js    ← PDF generation under load
tests/performance/k6/webhook-burst.js     ← webhook burst
tests/performance/k6/notification-burst.js← notification burst
tests/performance/k6/report-dashboard.js  ← report / dashboard load
tests/performance/k6/job-lease.js         ← background-job lease
```

Each script declares k6 thresholds mirroring the baselines. The
release pipeline fails when k6 reports `http_req_failed` above the
target or when the `p(95)`/`p(99)` thresholds exceed the baseline.

## Gates

- **PR pipeline**: nightly k6 smoke (1 minute, 5 VUs) against staging.
- **Release pipeline**: full k6 suite (10 minutes, 25 VUs) against
  staging. Production runs are never used for load.
- **Performance regression**: a 10% regression over the baseline
  warns; a 25% regression blocks.

## Resource leak checks

The performance suite also asserts on:

- No Chromium processes left behind after PDF generation.
- Postgres connection pool returns to the baseline after the test.
- Worker lease loops terminate cleanly.
- No orphaned blob URLs or temporary files.

These checks are part of the `tests/performance/resource-leaks.test.ts`
file (introduced at the start of Phase 10F).
